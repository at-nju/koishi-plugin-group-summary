# 群聊补课插件总体设计

状态：已确认，2026-08-01。

## 目标

为一个明确指定的群聊生成公开的补课站点。群友打开站点后，可以按最近活跃顺序浏览系统自动识别的话题，快速理解错过的讨论并继续参与。

第一版追求低维护、可控成本和足够完整的消息采集，不追求逐消息生成或浏览器实时推送。

## 系统形态

```text
NapCat / OneBot
      │ 实时事件 + 近期历史
      ▼
Koishi group-summary 插件（本地）
      ├─ 内容库：长期保存消息、图片与链接快照
      ├─ 每 10 分钟运行一次有界 Agent
      └─ 生成只含公开内容的发布快照
                              │ 出站上传
                              ▼
Cloudflare R2 ──────────> Cloudflare Pages
  发布数据快照              静态网页外壳 + 自定义域名
```

本地环境不提供公网入口。Pages 只在网页代码变化时部署；群聊内容更新只写入 R2。网页在打开或刷新时读取最新快照，不保持实时连接。

## 核心流程

### 消息采集

1. 只采集配置的目标群，且不区分群友消息与机器人消息。
2. 实时事件是主要入口；插件启动时及运行期间周期性拉取近期历史用于查漏。
3. 两条路径按平台消息标识去重后写入同一个本地内容库。
4. 首次启动尽可能导入平台仍能提供的近期历史，不尝试恢复更早的完整群史。
5. 第一版理解文字、图片和公开链接；不解析语音、视频及普通文件。
6. 链接在消息出现时提取标题、摘要和正文，之后不随目标网页变化而更新。

### 总结批次

每十分钟检查一次是否存在尚未处理的新消息。没有新消息时不调用模型，也不发布快照；存在新消息时启动一次有步骤和成本上限的 Agent。

Agent 的初始上下文包括本批新消息、必要的相邻消息，以及最近活跃的十个话题的精简目录。它可以按需展开单个话题，最终一次性提交完整变更集。每批只重新生成受影响的话题，不重读全部历史。

### 原子提交与发布

Agent 运行失败或达到上限时，不提交任何局部结果。变更集通过运行时校验后，以一次原子操作新建、修改、合并、拆分话题或调整消息归属。

本地提交成功后生成发布快照。发布时先上传一个完整的版本化快照，成功后再切换最新版本指针；R2 上传失败时，线上继续读取上一版本，本地将待发布版本留待重试，不重新调用 Agent。

## Agent 与确定性运行时的分工

Agent 负责需要语义判断的工作：

- 判断消息是否足以形成可见话题；
- 判断新消息属于最近话题还是新话题；
- 新建、修改、合并或拆分话题；
- 选择话题源；
- 生成标题、摘要及 Markdown 总结式正文。

确定性运行时负责系统完整性：

- OneBot 事件接收、历史补采与去重；
- 本地内容长期存储与批次游标；
- Agent 步骤、成本、超时和工具权限限制；
- 变更集结构校验及原子提交；
- 发布快照构建、R2 凭证使用和失败重试。

Agent 不直接访问 R2、不持有基础设施凭证，也不能任意删除本地内容。

## Agent 工具接口

工具接口保持小而深：

```text
get_recent_topics()
  返回最近活跃的 10 个话题及其精简内容。

get_topic_context(topic_id)
  按需返回一个话题的当前正文、话题源和必要上下文。

commit_changes(change_set)
  校验并原子提交整批话题变更；不允许产生一条消息归属多个主要话题、
  引用不存在的消息或只完成一半的合并与拆分。
```

本批新消息直接作为 Agent 的初始输入，不需要再通过工具读取。第一版不提供全历史搜索工具；目录之外的旧讨论即使主题相似，也可以形成新话题。

## 话题模型

话题由主题相似性与时间连续性共同决定。多个话题可以同时存在，一个话题可以短暂暂停后恢复；系统不写入不可修改的“已结束”状态。

“始终可修订”不表示相同主题永久属于同一个话题。相隔很远后重新出现的相似讨论通常形成新话题，且第一版只用最近十个话题作为关联候选。

每条消息最多属于一个主要话题，也可以暂时作为背景消息没有归属。系统可以在后续批次中重新判断。只有具有独立补课价值的内容才形成站点可见话题。

## 补课简报

每个话题使用统一外壳和总结式正文：

- 标题；
- 一两句话的摘要；
- 活跃时间，即第一条相关消息到最近一条相关消息的跨度；
- Markdown 总结式正文。

正文以总结为主，不使用固定栏目，也不内嵌原话引用。正文用连贯的段落叙述话题的起因、关键经过、各方观点、共识或结论与后续安排，读者不依赖原始消息也能读懂；结尾列出「相关人员」。话题宜大不宜碎：围绕同一件事的零散讨论合并为一个话题。新闻讨论可以突出新闻内容、不同观点和争议；约饭可以呈现提议、候选方案和最终安排。

存在明确起因时，新闻、链接、图片或原消息作为话题源突出展示。必须原样保留的关键原话（如公告、投票结果）可直接写入正文。正文使用 Markdown 表达，设计上不支持原始 HTML。

## 补课站点

首页是一条按最近相关消息时间倒序排列的话题流。旧话题重新活跃后回到前面。群友可以继续按时间加载更早话题，但第一版不提供搜索、标签或归档页。

站点只展示补课简报和话题源，不提供完整聊天记录。机器人不在群内发布摘要、更新通知或站点入口；群友直接访问已知域名。

第一版公开只读且不验证群成员身份，任何能访问域名的人都可以查看发布内容。

## 本地内容与发布数据

本地内容库是事实来源，长期保存目标群的文字、图片副本和链接快照，以便 Agent 继续修订话题。除非管理员主动清空整个数据集，否则第一版不自动清理；第一版也不处理消息撤回。

R2 不是内容库备份，只保存网页实际读取的发布快照。快照包含当前可见话题和简报，不包含背景消息、完整原始记录或图片文件。图片可以参与本地理解，但第一版不保证图片本身能在公开站点长期展示。

## 模型边界

第一版使用一个可配置的多模态 OpenAI 兼容模型，通过 `base URL`、`API key` 和 `model` 配置，不绑定具体厂商，也不引入多模型路由。

模型只在总结批次内由有界 Agent 调用。浏览器不调用模型，R2 和 Pages 也不承担总结计算。

## 首版不做

- 多群支持；
- 群成员认证和访问控制；
- 人工重命名、合并、拆分或审核话题；
- 完整聊天记录浏览；
- 站内搜索、标签和归档页；
- 机器人命令、入口或主动播报；
- 浏览器实时刷新或逐消息总结；
- 图片文件上传到 R2；
- 语音、视频及普通文件解析；
- 消息撤回处理；
- 全历史话题搜索与周期性全量重算。

## 实现前仍可调整的参数

以下是实现参数，不改变已经确认的产品与架构边界：

- 历史补采的重叠消息数量与重试间隔；
- Agent 最大步骤数、超时和成本上限；
- 本地数据表和变更集的具体结构；
- R2 快照命名、旧版本保留和缓存策略；
- Pages 前端技术栈与视觉样式；
- 具体多模态模型及提示词。
